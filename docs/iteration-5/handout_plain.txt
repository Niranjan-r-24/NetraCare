01
Where you are
You have the iteration 4 assistant: a LangGraph agent that answers from the clinic documents, routes patients to a speciality, and finds slots, books, cancels and reschedules through your clinic API, with Staff approval for late cancels and reschedules. So far you have checked it by hand, a few messages at a time. You have now learnt AI evals and LLMOps. This iteration adds no new patient feature. It measures what you have already built against the five targets in brief section 09, using larger test sets, and lets you see every LLM call, tool call, cost and delay while the app runs.

Watch your costs.
Every eval run calls the LLM many times: the app's own calls for each row, a judge call per chat reply, and several calls per row for RAGAS. As a rough guide, the small sets make around 150 to 200 calls per run and the large sets around 400 to 600, about a million tokens. With a small model that is usually a few US dollars or less, but this is an estimate, not a measurement: it depends on your model, your provider's prices and rate limits, and how many turns your agent takes. Run the small sets while you build, one suite at a time, check the cost in Opik after your first run, and run the large sets only when you need them.
Use agentic coding, and own the result
Let the AI write the runner and the scorers. Spend your time reading results and failing rows. You must be able to explain them in the final demo.
Understand the high-level flow:
the steps in section 04, from a golden dataset row to a number in your results.
Understand the important details:
why each target is scored the way it is, when code is enough and when you need an LLM judge, why the judge itself must be checked, and why the booking evals need a fixed clock.
Read the failing rows, not just the score.
A number tells you something is wrong; the trace tells you why.

How one eval run works
Load a golden set
from your repo, or from the dataset you uploaded to Opik.
Run each row through your real code:
the chat endpoint, the classifier, the answer function or the summary function. Every run is traced.
Score each row.
Use plain code wherever the answer can be checked exactly. Use an LLM judge only for meaning, such as "does this name a condition?".
Record the run as an experiment
in Opik, with every row, its output and its scores.
Write a basic report
with the five targets, the working bars and the failing rows, and exit with an error if a target is missed.

06
Rules and safety in this iteration
This iteration measures all five targets in brief section 09 for the first time, on larger test sets. It changes none of them, and none of the rules.
Safety rules
The red-flag target is 100%. A single missed red flag is a missed target, however good the rest looks.
Fix a failure in the app, not in the test. Don't edit golden rows, the judge labels or the clinic documents to make a score pass. If you think a label is wrong, say so in
summary.md
and leave it.
A safety score from a judge you haven't checked on
judge_calibration.csv
doesn't count.
Traces hold patient messages. Use only the synthetic data packs, never real patient information, and keep your Opik projects private.
Evals run on the eval database with the fixed clock, never on your normal database.
Keep your API and Opik keys in
.env
, as before.
